GIAP ON THE JETSON ORIN NANO - BUILD AND RUN
Written 2026-07-28. Device: nano.local, user "nano", repo at ~/goose-in-a-pond
===============================================================================

-------------------------------------------------------------------------------
READ THIS FIRST - THREE TRAPS
-------------------------------------------------------------------------------

1. NEVER use `cargo run`, and never omit `--release`.

   A plain `cargo run -p pond-server` builds WITHOUT the `cuda` feature. That
   gives you a CPU-only debug binary that runs llama.cpp on the 6 A78AE cores
   with no GPU at all. Worse, the non-CUDA code path leaves the model's
   `context_size` unset, so the `context_window_override` setting (16384)
   applies and the server tries to prefill a 16K-token context on CPU. Turns
   take minutes and the agent times out.

   This is not a configuration problem and `--native` is not the cause.

2. The nano's Node is v12.22.9. Vite 7 needs Node 20+.

   So `bash scripts/jetson.sh build --cuda` is NOT reliable on this device -
   it dies at its "Building web UI" step because `npm ci` fails under
   `set -e`. It also omits `pond-adapters-whisper/cuda` and
   `CMAKE_CUDA_ARCHITECTURES=87` that the deploy path uses.

   This is why deploy.sh builds the web UI on the Mac and rsyncs it over.

3. Only ONE server at a time.

   The systemd service holds port 8080. If you launch a second server manually
   without stopping it and do not pass --port, it binds 4000 and you then have
   two servers each loading a 3.1 GB model into 7.4 GB of unified memory, and
   the device swap-thrashes.

   CORRECTION: the port fallback is 4000..4009, NOT 80 -> 8080 -> 4000 -> 5000.
   ports::API_SERVER = 4000 and ports::MAX_TRIES = 10, so serve without --port
   starts at 4000 and walks upward. (AGENTS.md claimed the other order and was
   wrong; it has been corrected.) The server writes the port it actually bound
   to <data_dir>/.runtime_api_port - read that instead of guessing.


-------------------------------------------------------------------------------
THE EASY WAY: THE MENU
-------------------------------------------------------------------------------

Everything below is also available from one menu-driven script that auto-detects
the host, whether CUDA is usable, and the known bad states:

    bash scripts/giap.sh              # interactive menu
    bash scripts/giap.sh install      # first-time install (-y to skip prompts)
    bash scripts/giap.sh doctor       # health report; exits 1 on any FAIL
    bash scripts/giap.sh status       # detection banner only
    bash scripts/giap.sh build        # web UI + server, right features for THIS host
    bash scripts/giap.sh --dry-run .. # print every command instead of running it

It prints a detected-state banner first (host, L4T, CUDA, toolchain, repo +
submodule drift, web UI state, binaries, service scope, running server + port,
resources, Jetson power + over-current, display, data dir), then a numbered menu.
The doctor checks every trap in this document automatically.

It delegates to the existing scripts rather than duplicating them - deploys still
go through scripts/jetson.sh deploy.

-------------------------------------------------------------------------------
BUILD - OPTION A (RECOMMENDED): FROM THE MAC
-------------------------------------------------------------------------------

One command. Builds the web UI locally (Mac has Node 25), rsyncs dist to the
device, syncs the goose submodule, builds on-device with the correct CUDA
features, restarts the service and health-checks it.

    cd ~/Documents/Jarida/goose-in-a-pond
    bash scripts/jetson.sh deploy

Deploy another branch:

    bash scripts/jetson.sh deploy --branch my-branch

The branch must be pushed to the JETSON's `origin`, which is the
JERRYFROMKENYA fork - not jarida-io. Push to BOTH or the deploy builds stale
code:

    git push origin main && git push jarida-io main


-------------------------------------------------------------------------------
BUILD - OPTION B: ENTIRELY IN THE NANO'S TERMINAL
-------------------------------------------------------------------------------

This is what deploy.sh actually runs, minus the npm step that Node 12 breaks.

    cd ~/goose-in-a-pond
    git fetch origin && git reset --hard origin/main
    git submodule update --init --recursive

    PATH=$HOME/.cargo/bin:/usr/local/cuda/bin:$PATH \
    SQLX_OFFLINE=true CMAKE_CUDA_ARCHITECTURES=87 \
    cargo build -p pond-server \
      --features pond-adapters-local-inference/cuda,pond-adapters-whisper/cuda \
      --release

Notes:
  - `git submodule update` is REQUIRED. A parent-repo commit that bumps the
    goose pin does not move the submodule on the device. The nano ran for days
    on the right parent SHA with a stale submodule, missing the KV cache
    entirely. Verify with:  git submodule status
  - CMAKE_CUDA_ARCHITECTURES=87 makes ggml emit a real sm_87 cubin. Without it
    you ship compute_80 PTX that the driver JIT-compiles at first model load.
  - The dashboard embedded in the binary is whatever sits in
    pond-desktop/dist. Node 12 cannot refresh it, so a pure on-device build
    ships a stale UI until you rsync dist/ from the Mac:
        rsync -az --delete pond-desktop/dist/ nano:goose-in-a-pond/pond-desktop/dist/

There is no desktop app to build on this board. The shell is Electron and is
packaged for macOS only; this device's UI is the dashboard pond-server itself
serves, which is the same React bundle embedded at compile time. The board also
runs headless on purpose - gdm3 is disabled because GNOME held 2.6 GB of nvmap,
see docs/developer/jetson-device-tuning.md.

Timings from a full clean rebuild on 2026-07-28:
    pond-server release + CUDA ... 35m01s
An incremental build after a goose submodule bump was about 10m30s.

If you need disk before a big build: `target/debug` on the device is ~10 GB of
nothing and is safe to delete. A full `cargo clean` of both targets frees
about 21 GB.


-------------------------------------------------------------------------------
RUN: THE SERVICE
-------------------------------------------------------------------------------

    systemctl --user start goose-in-a-pond          # server on 8080

Then open http://nano.local:8080 from any machine on the LAN, or a browser on
the board's own panel if one is attached.

`serve --native` does nothing useful here: it prints that the desktop shell is
macOS-only and keeps serving. That used to be two documented run modes and a
trap about a stray debug binary shadowing the release one; both are gone with
the Tauri shell.

Service management:

    systemctl --user status  goose-in-a-pond
    systemctl --user restart goose-in-a-pond
    systemctl --user stop    goose-in-a-pond
    loginctl enable-linger nano      # survives SSH logout / starts at boot

Dashboard over the LAN:  http://nano.local:8080


-------------------------------------------------------------------------------
VERIFY YOU ARE ACTUALLY ON THE GPU
-------------------------------------------------------------------------------

The single most useful check. Run it after every build:

    grep -E "Applied Jetson Orin Nano CUDA|Applied Metal/platform" \
      ~/.local/share/goose-in-a-pond/logs/pond.log.$(date +%F) | tail -1

    "Applied Jetson Orin Nano CUDA settings"  -> correct, GPU build.
    "Applied Metal/platform settings"         -> CPU-only. Stop and rebuild.

Context window actually in force (should be 4096 on this device):

    grep "Applied Goose context" \
      ~/.local/share/goose-in-a-pond/logs/pond.log.$(date +%F) | tail -1
    # want: effective_ctx=4096 knobs=GOOSE_CONTEXT_LIMIT=4096;...

Health and process count:

    curl -s http://127.0.0.1:8080/api/v1/health
    ps aux | grep "[p]ond-server"        # want exactly one

Per-turn performance, with the KV cache working:

    grep -E "prefill plan|turn_end" ~/.local/share/goose-in-a-pond/logs/pond.log.$(date +%F) | tail

Healthy pattern for one session: turn 1 CreateContext, then ReusePrefix on
every later turn, with SacrificialContext in between for the memory-extraction
call (that one is correct and leaves the chat cache intact). Seeing
FullPrefillInPlace on turn 2 means something changed the system prompt between
turns.

Reference numbers measured on this device, 2026-07-28, gemma-4-E2B-it Q4_K_M:

    turn 1 (fresh):  3252 prompt tokens, ttft 4639 ms, prefill 4444 ms,
                     decode 26.0 tok/s, model load 6736 ms
    turn 2 (reuse):  ttft 550 ms, prefill 327 ms
    turn 3 (reuse):  ttft 901 ms, prefill 423 ms
    turn 4 (reuse):  ttft 847 ms, prefill 469 ms
    context: 4096, sitting at ~84% used

Note: turns 2-4 generated only 4-8 tokens each, so their decode tok/s figures
are measurement noise. Turn 1's 26 tok/s over 122 tokens is the real rate.


-------------------------------------------------------------------------------
OTHER GOTCHAS
-------------------------------------------------------------------------------

  - `pkill -f pond-server` over SSH kills your own shell, because the remote
    command line contains the pattern. Use the explicit PID, or `[p]ond-server`.

  - Do not run a chat or load a model while a release build is linking. The
    linker gets OOM-killed.

  - Three git remotes: origin = JERRYFROMKENYA fork (what the JETSON pulls),
    jarida-io = org repo, exile10. Push both.

  - Logs live at ~/.local/share/goose-in-a-pond/logs/pond.log.YYYY-MM-DD .
    There is no journald output; the service writes to those files.
    Timestamps in the logs are UTC. The device clock is EAT (UTC+3), so
    11:06:59Z in the log is 14:06:59 on the device.


-------------------------------------------------------------------------------
KNOWN OPEN ITEMS (as of 2026-07-28, after the context fix)
-------------------------------------------------------------------------------

  RESOLVED since the first version of this document:

  - Conversations no longer cut off after 3-4 turns. Nothing used to reserve
    room for the model's own output, so a thinking block overran the 4096
    window mid-generation, llama.cpp raised ContextLengthExceeded, and goose
    compacted the conversation away through a path that ignores
    GOOSE_AUTO_COMPACT_THRESHOLD. Fixed by CompactionProfile.output_reserve_tokens
    plus context_size 4096 -> 16384. Verified: a 6-turn conversation with a 4 KB
    tool result now completes with 0 compactions, context at ~50%.
  - context_window_override is now 0 on the device.
  - The stale /etc/systemd/system unit from an old install.sh run is removed.
  - Power mode is 25W, not MAXN_SUPER: one identical turn produced 1,176
    over-current events under MAXN_SUPER versus 44 at 25W, for a 5% decode
    difference. Both modes clock memory at 3199 MHz and GIAP decode is
    memory-bandwidth-bound, so MAXN_SUPER buys almost nothing on this workload.
  - apply_platform_settings now says CPU-ONLY on aarch64 Linux instead of
    "Metal/platform ... n_gpu_layers=99", which read like a working GPU build.
  - embedded_ui_present compared a 20-byte window to a 21-byte marker and so
    always returned true; the placeholder warning can now actually fire.

  STILL OPEN:

  - tool_selection_mode is "all": 61 tools, ~2,650 of the prompt's tokens.
    Switching to "relevant" measured 59 tools/6,539 tokens -> 17 tools/2,386 on
    the Mac. Now an optimisation rather than a necessity, and it wants its own
    burn-in: on a 2B model the escape hatch was only used when asked explicitly.
  - TTS has only the German voice installed (de_DE-thorsten-medium).
  - home_name in Settings is empty.
  - `giap.sh` writes a build stamp; `jetson.sh deploy` does not, so the doctor
    reports build provenance as UNKNOWN after a deploy.
